## 通用约定

### HTTP 状态码约定

所有客户端接口业务错误**始终返回 HTTP status 200**。客户端通过 JSON body 中的 `code` 字段区分业务结果，无需关注 HTTP 状态码。

### 请求头

| Header          | 必填 | 说明                                                                                    |
|-----------------|------|-----------------------------------------------------------------------------------------|
| `Content-Type`  | 是   | `application/json`（默认）或 `application/x-protobuf` / `application/protobuf`（可选） |
| `Authorization` | 是   | `Bearer <token>`，Token 由登录接口获取                                                  |

> 响应格式与请求 `Content-Type` 保持一致：发 JSON 收 JSON，发 protobuf 收 protobuf。

### 序列化格式

服务端统一根据请求的 `Content-Type` 决定上下行的序列化格式，请求与响应格式保持一致。

| Content-Type                                              | 请求解析方式      | 响应序列化方式  |
|-----------------------------------------------------------|-------------------|-----------------|
| `application/json`（或不填）                              | JSON              | JSON            |
| `application/x-protobuf` / `application/protobuf`        | Protobuf 二进制   | Protobuf 二进制 |

Proto 定义见 `pb/cs.proto`（通用结构见同包 `pb/def.proto`，C# 命名空间均为 `Cspb`），相关消息：`MailListReq`、`MailListResp`、`MailReadReq`、`MailReadResp`、`MailReceiveReq`、`MailReceiveResp`、`MailReceiveAllReq`、`MailReceiveAllResp`、`MailDeleteReq`、`MailDeleteResp`、`ErrorResp`。

> **错误响应的 protobuf 兼容性**：所有 `*Resp` 消息的前两个字段（tag 1 = `code`，tag 2 = `message`）与 `ErrorResp` 保持一致，客户端可直接用具体 `*Resp` 类型解析错误响应，无需额外处理。

### 统一响应结构（JSON 模式）

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

| 字段      | 类型   | 说明                                     |
|-----------|--------|------------------------------------------|
| `code`    | int    | `0` 表示成功，非 `0` 为业务错误码       |
| `message` | string | 结果描述，成功时为 `"ok"`                |
| `data`    | object | 成功时的业务数据，失败时为 `null` 或省略 |

> 例外：`POST /api/mail/delete` 响应无 `data` 包装，`deleted` 为顶层字段（见[清理已读邮件](#清理已读邮件)）。

### 时间戳

所有时间戳（`createTime`、`expireTime`）均为 **Unix 毫秒**。

## 邮件业务规则

### 邮箱容量

- 每位玩家邮件上限为 **100 封**（含已过期、未读等所有状态）。
- 列表接口会触发 **Lazy Create**：自动补发尚未下发的系统邮件模板（全服邮件 / 定向邮件），补发前若邮箱超出上限，服务端按以下优先级腾出空间：
  1. 已过期邮件
  2. 附件已领取的最旧邮件
  3. 最旧邮件（兜底）
- 若腾出空间后仍不足以容纳全部待补发邮件，多余的系统邮件模板将被丢弃（仅记录服务端日志），客户端无感知。

### 邮件状态与过期

- 邮件包含两个状态位：**已读（read）** 与 **附件已领取（rewarded）**。
- `expireTime`：**绝对过期时间戳（Unix 毫秒）**，从玩家收到邮件时刻开始计算（服务端已由相对有效期换算）；系统模板邮件必有过期时间，运营未配置相对有效期时默认按 7 天计算。
- 已过期邮件（`expireTime < 当前时间`）：**不出现在列表中**，**不可查看 / 不可领取**，客户端按"邮件不存在"处理。

### 预发布与生效窗口

- 系统邮件模板支持**预发布**：运营侧可指定 `startTime`（预发布生效开始）与 `endTime`（预发布结束），仅当**服务器时间处于 `[startTime, endTime]` 区间内**，邮件才会在玩家拉取邮件列表时下发。
- `startTime` 未设置（`0`）表示立即生效；`endTime` 未设置（`0`）表示不限制结束时间。
- 同一模板对每个玩家**终生只下发一次、附件终生只领取一次**（按 `playerId + templateId` 去重）。
- 客户端无需感知预发布窗口：未到生效时间的邮件不会出现在列表中；窗口结束后，已下发的邮件仍按自身 `expireTime` 存活直至过期。

### 排序规则

列表按以下规则排序：
1. `status` 升序：未读（未读未领）→ 已读 → 已读且已领
2. 同状态下按创建时间倒序（新邮件在前）

### 发奖说明（重要）

服务端**不直接发放奖励**。领取接口仅负责：

1. 在数据库中原子标记该邮件附件为"已领取"（防止重复领取 / 并发作弊）；
2. 返回本次领取的奖励清单（`rewards`）。

奖励的实际到账由客户端根据返回的 `rewards` 自行处理。

## 获取邮件列表

### `GET /api/mail/list`

获取当前玩家的邮件列表（含未过期、已读、未读、已领取等状态）。每次请求会触发系统邮件 Lazy Create 补发。

#### 请求参数（Query String）

| 参数    | 类型  | 必填 | 说明                                                           |
|---------|-------|------|----------------------------------------------------------------|
| `start` | int64 | 否   | 起始索引（闭区间，从 0 开始），默认 `0`                       |
| `end`   | int64 | 否   | 结束索引（闭区间），默认 `19`（即默认返回前 20 条）           |

> 分页说明：`end < start` 时服务端重置 `end = start + 19`；单页最多返回 **50** 条。客户端可通过"已返回条数 < 请求条数"判断列表是否已到末尾，服务端不提供总条数 / `hasMore` 字段。

#### 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "mails": [
      {
        "mailId": 100001,
        "title": { "type": 0, "text": "新手礼包" },
        "sender": "系统",
        "hasReward": true,
        "isRead": false,
        "isRewarded": false,
        "createTime": 1780000000000,
        "expireTime": 1783000000000
      }
    ]
  }
}
```

`data.mails` 每项结构：

| 字段          | 类型    | 说明                                            |
|---------------|---------|-------------------------------------------------|
| `mailId`      | int64   | 邮件唯一标识，后续 read / receive 接口使用      |
| `title`       | object  | 邮件标题（`TextContent` 结构，见下文）          |
| `sender`      | string  | 发送者名称                                      |
| `hasReward`   | bool    | 是否携带附件                                    |
| `isRead`      | bool    | 是否已读                                        |
| `isRewarded`  | bool    | 附件是否已领取                                  |
| `createTime`  | int64   | 创建时间戳（Unix 毫秒）                         |
| `expireTime`  | int64   | 绝对过期时间戳（Unix 毫秒），从收到邮件时刻开始计算；系统模板邮件必有过期时间（未配置时默认按 7 天计算），非模板邮件可为 `0` 表示永不过期 |

> 列表项**不含邮件正文与奖励明细**，客户端展示详情时调用[查看邮件详情](#查看邮件详情)。

#### `TextContent` 结构

用于邮件标题/正文等可本地化字段：

| 字段   | 类型   | 说明                                                                    |
|--------|--------|-------------------------------------------------------------------------|
| `type` | int32  | 文本类型：`0`=纯文本（None），`1`=多语言Key（Lc）                       |
| `text` | string | `None` 类型为原文本内容，直接展示；`Lc` 类型为多语言Key，由客户端按当前语言自行解析展示 |

#### 错误响应

| 业务错误码 | message                     | 说明                         |
|------------|-----------------------------|------------------------------|
| `2400`     | `invalid request parameters` | 请求参数解析失败             |
| `2401`     | `missing authorization token` | 未携带有效 Token，需重新登录 |
| `2500`     | `internal server error`     | 服务端内部错误               |

## 查看邮件详情

### `POST /api/mail/read`

查看单封邮件正文与奖励明细，并将邮件标记为**已读**（已读邮件重复调用不会产生副作用）。

#### 请求体

```json
{
  "mailId": 100001
}
```

| 字段     | 类型  | 必填 | 说明           |
|----------|-------|------|----------------|
| `mailId` | int64 | 是   | 邮件唯一标识   |

#### 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "mailId": 100001,
    "title": { "type": 0, "text": "新手礼包" },
    "content": { "type": 0, "text": "欢迎来到游戏，以下是给你的见面礼！" },
    "sender": "系统",
    "rewards": [
      { "itemId": 1001, "count": 5 },
      { "itemId": 2001, "count": 1000 }
    ],
    "isRead": true,
    "isRewarded": false,
    "createTime": 1780000000000,
    "expireTime": 1783000000000
  }
}
```

| 字段          | 类型             | 说明                                                |
|---------------|------------------|-----------------------------------------------------|
| `mailId`      | int64            | 邮件唯一标识                                        |
| `title`       | object           | 邮件标题（`TextContent` 结构）                      |
| `content`     | object           | 邮件正文（`TextContent` 结构）                      |
| `sender`      | string           | 发送者名称                                          |
| `rewards`     | array\<Reward\>  | 附件奖励列表，无附件时为空数组                      |
| `isRead`      | bool             | 是否已读（本接口调用成功后通常为 `true`）           |
| `isRewarded`  | bool             | 附件是否已领取                                      |
| `createTime`  | int64            | 创建时间戳（Unix 毫秒）                             |
| `expireTime`  | int64            | 绝对过期时间戳（Unix 毫秒），从收到邮件时刻开始计算；系统模板邮件必有过期时间（未配置时默认按 7 天计算），非模板邮件可为 `0` 表示永不过期 |

`Reward` 结构：

| 字段     | 类型  | 说明     |
|----------|-------|----------|
| `itemId` | int32 | 道具 ID  |
| `count`  | int64 | 数量     |

#### 错误响应

| 业务错误码 | message             | 说明                                                        |
|------------|---------------------|-------------------------------------------------------------|
| `2400`     | `mailId is required` | 缺少 `mailId` 或小于等于 0                                  |
| `2401`     | `missing authorization token` | 未携带有效 Token，需重新登录                    |
| `2420`     | `mail not found`     | 邮件不存在 / 已过期 / 不属于当前玩家                        |
| `2500`     | `internal server error` | 服务端内部错误                                            |

## 领取单封附件

### `POST /api/mail/receive`

领取单封邮件的附件。领取成功后邮件同时被标记为**已读 + 附件已领取**。

服务端采用原子校验（附件未领取才允许置位），**并发重复请求只会成功一次**，不会重复发放。

#### 请求体

```json
{
  "mailId": 100001
}
```

| 字段     | 类型  | 必填 | 说明           |
|----------|-------|------|----------------|
| `mailId` | int64 | 是   | 邮件唯一标识   |

#### 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "rewards": [
      { "itemId": 1001, "count": 5 },
      { "itemId": 2001, "count": 1000 }
    ]
  }
}
```

| 字段      | 类型            | 说明                                      |
|-----------|-----------------|-------------------------------------------|
| `rewards` | array\<Reward\> | 本次领取的奖励清单（客户端据此自行发奖） |

#### 错误响应

| 业务错误码 | message                 | 说明                                            |
|------------|-------------------------|-------------------------------------------------|
| `2400`     | `mailId is required`    | 缺少 `mailId` 或小于等于 0                      |
| `2401`     | `missing authorization token` | 未携带有效 Token，需重新登录           |
| `2420`     | `mail not found`        | 邮件不存在 / 已过期 / 不属于当前玩家            |
| `2421`     | `mail has no reward`    | 该邮件无附件，不可领取                          |
| `2422`     | `reward already received` | 附件已领取（含并发重复请求）                 |
| `2500`     | `internal server error` | 服务端内部错误                                  |

## 一键领取所有附件

### `POST /api/mail/receiveAll`

一次性领取所有**有附件、未领取、未过期**邮件的附件，并将所有**无附件的未读邮件**标记为已读（消化纯通知邮件）。

无请求参数，玩家身份由 Token 解析。

#### 请求体

```json
{}
```

（无需任何字段）

#### 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "rewards": [
      { "itemId": 1001, "count": 10 },
      { "itemId": 2001, "count": 3000 }
    ],
    "count": 3
  }
}
```

| 字段      | 类型            | 说明                                                  |
|-----------|-----------------|-------------------------------------------------------|
| `rewards` | array\<Reward\> | 本次合并领取的全部奖励清单（同道具自动聚合数量）      |
| `count`   | int32           | 本次成功领取附件的邮件数量（无附件邮件不计入）        |

> 说明：`rewards` 已按 `itemId` 合并聚合，客户端可直接按聚合后的清单一次性发奖。

#### 错误响应

| 业务错误码 | message                     | 说明                         |
|------------|-----------------------------|------------------------------|
| `2401`     | `missing authorization token` | 未携带有效 Token，需重新登录 |
| `2500`     | `internal server error`     | 服务端内部错误               |

## 清理已读邮件

### `POST /api/mail/delete`

删除当前玩家**所有已读**且**可清理**的邮件。可清理的定义：

- 无附件；或
- 附件已领取

**含附件但尚未领取的邮件不会被删除**（保护玩家未领取的奖励）。已过期但未读的邮件不在删除范围内，由服务端定时任务另行清理。

无请求参数，玩家身份由 Token 解析。

#### 请求体

```json
{}
```

（无需任何字段）

#### 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "deleted": 5
}
```

> 注意：本接口响应**无 `data` 包装**，`deleted` 为顶层字段。

| 字段      | 类型  | 说明                     |
|-----------|-------|--------------------------|
| `deleted` | int64 | 本次实际删除的邮件数量   |

#### 错误响应

| 业务错误码 | message                     | 说明                         |
|------------|-----------------------------|------------------------------|
| `2401`     | `missing authorization token` | 未携带有效 Token，需重新登录 |
| `2500`     | `internal server error`     | 服务端内部错误               |

## 错误处理

### 错误码总览

| 业务错误码 | message                    | 触发场景                               |
|------------|----------------------------|----------------------------------------|
| `2400`     | `invalid request parameters` / `mailId is required` | 请求参数非法           |
| `2401`     | `missing authorization token` | 未认证或 Token 失效，需重新登录      |
| `2420`     | `mail not found`           | 邮件不存在 / 已过期 / 不属于当前玩家   |
| `2421`     | `mail has no reward`       | 邮件无附件，不可领取                   |
| `2422`     | `reward already received`  | 附件已领取（含并发重复请求）           |
| `2500`     | `internal server error`    | 服务端内部错误                         |

### 客户端建议处理策略

| 错误码 | 处理方式                                                                              |
|--------|---------------------------------------------------------------------------------------|
| `2400` | 检查请求参数（如 `mailId` 合法性），修复后重试                                       |
| `2401` | Token 失效，重新调用 `/auth/login` 获取新 Token 后重试                               |
| `2420` | 邮件不存在或已过期：从本地列表移除该邮件；若为过期场景，无需重试                    |
| `2421` | 无附件邮件不可领取：隐藏领取按钮，只展示内容                                          |
| `2422` | 附件已领取（或重复请求）：幂等处理，视为成功即可，无需报错                          |
| `2500` | 服务端内部错误：弹出提示，提供"重试"按钮；可上报客户端日志辅助排查                  |
| 网络错误（超时 / 无响应） | 检查网络连接后重试；`receive` / `receiveAll` 已做幂等处理，重复请求不会重复发放 |
